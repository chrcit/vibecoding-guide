## Curriculum review

### What landed for a sceptical backend engineer at `deep`

- **Honest threat modeling without hand-waving.** The single biggest trust builder in this run was the combination of Turn 3 (*T3 Code is not a sandbox; permission modes govern approval prompts, not filesystem reach; workspace-scoped file tools don't bound shell commands*), Turn 4 (*raw script stdout enters the next model request*), and Turn 9 (*`AGENTS.md` is advisory text weighed by the model, not code enforcement*). A sceptical backend engineer who has been burned by marketing claims about "safe AI sandboxes" immediately relaxes when the tool refuses to oversell its own boundaries.
- **Change-audit table (Turn 6) & honest Git snapshot boundary (Turns 5–8).** Separating tracked revert (`analyze_webhooks.py`) from untracked post-snapshot files (`runbook.md`, `__pycache__/`)—and refusing to silently invent a Git author or commit `__pycache__/`—felt genuinely engineering-grade. Explicitly putting prompts, read files, and tool outputs under *Left this machine* (while distinguishing zero script egress) eliminated the usual annoyance of vague privacy reassurances.
- **Returning-session restraint (`G1`) & `AGENTS.md` table adherence.** Skipping the first-session scaffold and using tables consistently made the 11-turn run feel crisp rather than pedagogical.

### Curriculum & skill gaps to tighten

1. **Codify two backend threat-model facts in `mechanisms/world.md` (`deep`) (`curriculum`, medium):** On Turns 3–4, this model happened to improvise two insights that made L5 land hard for a backend engineer: (a) built-in file tools may enforce workspace boundaries, while shell commands execute with the host OS user's full reach; and (b) tool stdout/stderr enters the next model request, so running a local script on sensitive files still exfiltrates secrets if raw lines or tracebacks print to stdout. Neither is stated explicitly in `world.md` `deep`, so other models/runs may miss them. Adding one tight sentence covering both makes `deep` L5 reliably concrete.
2. **Scope Git snapshot staging and undo to named files in `mechanisms/world.md` (`curriculum`, medium):** On Turn 8, the agent ran `git restore .` across the whole working tree. That was harmless in our clean fixture, but on a backend engineer's real dirty repo with unrelated unstaged work, `git restore .` would silently destroy edits from outside the session (just as `git add -A` would sweep in `.env` or caches). `world.md` *Snapshots, honestly* should explicitly specify staging only the listed files (`git add <files>`, never `git add -A`) and reverting only the specific modified files (`git restore <files>`, not blanket `git restore .`).
3. **Give Antigravity learners a practical persistence fallback in `mechanisms/text.md` (`curriculum`, low):** Turn 11 was completely honest that Antigravity under T3 Code does not auto-load `AGENTS.md`, which turns the fresh-thread handover test into a confirmation of non-autoload rather than a working persistence workflow. Adding one sentence naming the practical fallback on non-autoloading harnesses (e.g., referencing `@AGENTS.md` / `"read AGENTS.md first"` in a fresh thread, or putting recurring rules in a `$skill`) gives the learner a real next step instead of a dead end.
4. **Add foreground/surface CSS tokens to `moves.md` (`papercut`, low):** `moves.md` lists `--primary` and `--accent` without `--primary-foreground`, `--accent-foreground`, or `--accent-surface`. On Turn 2, the model guessed `#27272a` as a fallback for `--accent` and paired `background: var(--accent)` with `color: var(--foreground)`, producing dark-on-blue low-contrast text on `.btn.active` in light mode. Naming `--primary-foreground`, `--accent-foreground`, and `--accent-surface` in `moves.md` removes that trap.
5. **Reinforce `**Try:**` adaptation in `mechanisms/world.md` (`papercut`, low):** Even with `SKILL.md` asking to reword `**Try:**` lines to the learner's work, Turn 4 copied `world.md`'s `"same columns and kinds of values as mine"` verbatim for JSONL webhook logs. Marking the `world.md` template clearly as a pattern to adapt (or making its wording less spreadsheet-specific) reduces verbatim copy-paste slips.

### `moves.md` sentences: what this persona would actually reuse

- **Would definitely keep and reuse:**
  - *"What did you change on my computer today? Group it into files, commands and anything that left this machine."* — Immediately useful as an end-of-session audit in any repo.
  - *"Make me invented data with the same [schema/fields] as mine, and build the method on that first."* — Directly matches how security-conscious backend engineers debug prod parser bugs without leaking customer payloads or tokens.
  - *"Before you come back to me, run it on five weirder edge-case inputs—including one that should break it—and show me what happens."* — Concrete, verifiable, zero fluff.
  - *"What does this command do, and why do you need it?"* (in Supervised mode) and *"Put the files back the way they were in the snapshot, and show me what's still left on disk."* — Both map directly to everyday engineering hygiene.
  - Dragging / `@`-referencing a past thread to summarize edge cases or extract a skill.
- **Would skip or rewrite:**
  - Spreadsheet-flavored wording like *"same columns"* or *"build the method"* — an engineer naturally says *"same JSONL schema/fields"* and *"reproduce the edge case"*.
  - Generic *"Show me in a picture"* prompts unless tied to a concrete diagnostic (like the p95 latency / flaky endpoint dashboard, which *did* earn its keep once compact).
